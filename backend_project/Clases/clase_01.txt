Introduccion a Backend


En el mundo del frontend, existen diferentes plataformas como una web app, una app mobile, y cualquier tipo de plataforma desarrollada para un dispositivo que se puede
conextar a internet. Pero, para cada una de ellas, se programan de una manera particular.
El backend (un servidor) es universal, lo que quiere decir que un backend es consumido sin importar de que origen sea el dispositivo del que se le hace una solicitud.
El backend puede alojar informacion, consultar informacion a una base de datos, define rutas a las cuales un frontend puede consultar, posee validaciones para rebotarle
al frontend las peticiones cuando su peticion no coincide con lo esperado.

Arquitectura cliente-servidor: Dentro del desarrollo web, esta arquitectura hace refrencia a un modelo de comunicacion que vincula a varios dispositivos con un servidor
a traves de internet.
	- Cliente: Son los dispositivos que hacen peticiones de servicios o recursos a un servidor. Pueden ser una PC, telefono celular, tablet, consola de videojuegos,
	o cualquier implemento que tenga la capacidad de conectarse a una red. Dentro de internet, el cliente suele acceder a estos servicios y recursos a traves de un
	navegador web.
	- Servidor: Es el equipo que brinda los servicios y recursos a los que acceden los clientes. Es importante tener en cuenta que la misma computadora puede ser el
	cliente y el servidor al mismo tiempo. De hecho es lo mas normal en el entorno de desarrollo de un sitio o aplicacion web.
Cuando el frontend hace una peticion al backend, se manda un objeto request. El backend contesta con un objeto de response. Esto se denomina flujo cliente-servidor:
	- Request: Es la solicitud que hacemos a traves del navegador, es decir, desde el cliente al servidor.
	- Response: El servidor recibe dicha solicitud, la procesa y la envia como respuesta al cliente (navegador).

Creacion de directorio backend:

Solo utilizamos Node.JS para ejecutar JS del lado del servidor/backend. Ademas vamos a utilizar un framework de Node.JS llamado Express.Js.
Express habilita una forma mas practica y comoda de poder crear un servidor, y ademas un sistema de enrutado mas practico que la forma pura de Node.Js.
No existe la consola desde el lado del backend, ya que la consola es una de las solapas del navegador. Pero Node,js conservo console.log, pero solo 
para imprimir en la terminal del IDE.
	1. Con npm init -y creamos un proyecto de node con todo configurado de base (-y dice que si a todo).
	2. Intalamos node modules con npm i
	3. Instalamos express
	4. Creamos la carpeta src para el codigo fuente. Dentro posee el archivo app con el cual vamos a ejecutar el backend.

Archivo app:

1. Importamos express. Express posee las siguientes propiedades: 
    - aplication: Posee todos los metodos necesarios para manejar una apicacion backend.
        - use: Lo usamos para ejecutar routers o alguna funcion importante.
        - get, post, delete, y put. Nos permiten configurar rutas de este tipo.
    - request: Esta propiedad gestiona el objeto que envia el frontend al backend.
    - response: Esta propiedad gestiona el objeto que se responde al frontend desde el backend.
    - Routers: Nos permite crear routers.
    - json: Nos permite traducir texto plano a JSON.
2. Ejecutamos express, almacenandolo en una variable, para levantarla y crear el servidor. 
3. Para poder ver el contenido/rutas del servidor es necesario definir un puerto. Tenemos metodos como:
    - listen: NOs permite escuchar el servidor en tal puerto.
React, Angular, Vue usan el 3000, por lo que usamos otro diferente.
4. Ejecutamos una escucha del servidor en el puerto definido.

Como no podemos tener todas las configuraciones en un solo archivo, se crean:

- Directorio server: En el archivo server colocamos la importacion de express y su ejecucion. Exportamos dicho contenido para que lo pueda usa app.

La estructura de las routes es:
    app.metodo("/ruta", logica)
Logica es una funcion flecha que recibe como parametro request, response. Con "_" se indica que en tal seccion no va nada. COn el response configuramos
lo que se quiere resoponder al frontend. Por ejemplo:

    app.get("/", (_, response) => {
        response.send("Bienvenido a mi primer servidor")
    })

    app.get("/producto", (_, response) => {
        response.json({nombre: "Termo", precio: 10000})
    })

Cuando los metodos son diferentes pero el endpoint es el mismo, no hay problema. Pero si los metodos son iguales si hay colision.


Routers tematicos: Los creamos para evitar la repeticion de palabras en los endpoints. 
Como el archivo server se empieza a llenar de cosas, llevamos las rutas a archivos independientes en un directorio routes. Para ambos archivos
importamos express, el Router de cada uno y las rutas que corresponden a cada uno. En server importamos los Routers de cada archivo.
Asi tenemos los archivos:
- cosmeticos.routes.js:

    const express = require("express");

    const cosmeticosRouter = express.Router();   // localhost:4000/cosmeticos

    const app = express();

    cosmeticosRouter.get("/productos", (_, response) => {
        response.json({nombre: "Lapiz labial", precio: 8000})
    })


    module.exports = cosmeticosRouter;

- ferreteria.routes.js:

    const express = require("express");

    const ferreteriaRouter = express.Router();   // localhost:4000/ferreteria

    const app = express();

    ferreteriaRouter.get("/productos", (_, response) => {
        response.json({nombre: "Llave de tuerca", precio: 10000})
    })

    module.exports = ferreteriaRouter;

- server.js:

    const express = require("express");
    const ferreteriaRouter = require("../routes/ferreteria.routes")
    const cosmeticosRouter = require("../routes/cosmeticos.routes")

    const app = express();

    app.use("/cosmeticos", cosmeticosRouter)
    app.use("/ferreteria", ferreteriaRouter)


    app.get("/", (_, response) => {
        response.send("Bienvenido a mi primer servidor")
    })


    module.exports = app;

Nosotros buscamos llevarnos la logica de las rutas a otro lado para que no crezcan desmedidamente, y usamos los archivos de routes para la ejecucion de las rutas.
Para evitar la acumulacion de codigo, creamos un directorio controllers y llevamos la logica de cada parte a su correspondiente archivo.
En cada archivo podemos tener varias funciones, entonces las podemos exportar dentro de un solo objeto. A las mismas las importamos en los routes.
- ferreteria.controller.js:

    const getAllProducts = (_, response) => {
        response.json({nombre: "Llave de tuerca", precio: 10000})
    }

    module.exports = {getAllProducts}

- ferreteria.routes.js:

    const express = require("express");
    const {getAllProducts} = require("../controllers/ferreteria.controller");

    const ferreteriaRouter = express.Router();   // localhost:4000/ferreteria

    const app = express();

    ferreteriaRouter.get("/productos", getAllProducts);

    module.exports = ferreteriaRouter;



- cosmeticos.controller.js:

    const getAllProducts = (_, response) => {
        response.json({nombre: "Lapiz labial", precio: 8000})
    }

    module.exports = {getAllProducts}

- cosmeticos.routes.js:

    const express = require("express");
    const { getAllProducts } = require("../controllers/cosmeticos.controller");

    const cosmeticosRouter = express.Router();   // localhost:4000/cosmeticos

    const app = express();

    cosmeticosRouter.get("/productos", getAllProducts)


    module.exports = cosmeticosRouter;

Tenemos una serie de datos que no queremos que se vean al hacer un push en github. 
    - Archivo .env (environment): Posee variables de entorno que afectan a la aplicacion pero que no queremos que nadie las vea. Una de las cosas que colocamos dentro de
    este archivo son los puertos, contraseñas, endpoints, usuarios, etc.
    Para poder acceder desde un archivo app, necesitamos una libreria externa llamada dotenv. Para poder usarla necesitamos:
        require('dotenv').config()
    Para acceder a las variables que contiene el archivo .env, hacemos por ejemplo:
        const PORT = process.env.PORT
EJecutamos el servicio fuera del directorio src para que se detecte el archivo .env.
- app.js:

    const app = require("./server/server");
    require('dotenv').config()

    const PORT = process.env.PORT

    app.listen(PORT, () => console.log(`Servidor corriendo en el puerto ${PORT}`))

Vamos a hacer una aplicacion de autos y vamos a trabajar con una DB externa. Y vamos a utilizar Mongo DB para la DB.
Configuramos la cuenta con google:
1. Le damos a CREATE CLUSTER y elejimos el plan FREE
2. Dejamos por defecto Brasil, AWS y le damos un nombre al cluster. Damos a crear.
3. En el menu de inicio vamos a la seccion SECURITY -> DATABASE & NETWORK ACCESS.
4. Entramos en Add New Database User, colocamos un usuario y contraseña.
5. En la seccion Built-in Role damos permisos Atlas admin, y damos a add user.
6. Entramos en NETWORK ACCESS -> ADD IP ADDRESS, e ingresamos 0.0.0.0/0 para acceso publico. En comentarios podemos acceso publico. Damos a confirmar.
7. Vamos a la seccion DATABASE -> CLUSTERS. Apretamos en Connect y vamos a la parte de Compass. Compass es una plataforma interactiva donde podemos recorrer la BD
a traves de una interfaz. Debemos instalarla asi que elegimos el SO, en mi caso Ubuntu.
Mongo no necesita SQL, ya que al ser no relacional tiene otros metodos para pegarle a la DB mediante la mongo shell.
8. Una vez descargado el compass, en la seccion de OVERVIEW -> CLUSTERS -> CONNECT -> COMPASS, se nos provee un enlace que nos permite conectarnos a la BD en cuestion.
Un cluster es como una especie de biblioteca que puede tener multiples BDs, las cuales pueden tener multiples conelecciones. Una coleccion es una especie de array con muchos
objetos, y la estructura de dichos objetos va a depender de lo que la coleccion espera.
9. Abrimos el software de compass y damos a nueva conexion. Pegamos el enlace e introducimos en las secciones que corresponden el usuario y contraseña creados inicialmente.
El manejo de compass se ve en la clase 2.
